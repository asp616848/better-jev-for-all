# ViZDoom harness (text arm)

PRD.md Sections 8.1 item 2 / 8.1d. See `benchmarks/README.md` for the
cross-benchmark design; this file covers what's specific to ViZDoom.

**Status: built and validated end to end with the rubric-oracle, random, and
mock policies -- not yet run against a real trained checkpoint.** No GPU was
touched building this (a ~6-hour training run, `checkpoints/
ekvachan-decoder-qwen-vision`, was active on this server throughout). The
real text-arm run against `checkpoints/ekvachan-decoder-qwen-benchcorpus` is
one command, listed below, for the coordinating session once the GPU is free.

## What this is

`Defend the Center` and `Health Gathering`, the two scenarios Von's own
published headline claim (**9.00 kills vs Jev's 5.62**) is based on, run on
Von's own published 8-seed-per-scenario protocol so the comparison is
like-for-like. Unlike JevBench/jabr-v2/ScreenSpot-v2, there is no frozen
dataset here -- the item sequence is generated by a live, closed-loop ViZDoom
episode reacting to the policy's own actions. `benchmarks/common/
episodic.py::run_episodic_harness()` is the new loop this required; see its
own docstring for why it's a separate function from `run_harness()`.

**Observation is text, not vision** (PRD.md 8.1d, verified against Von's own
published `benchmarks/doom_eval.py`/`run_doom_benchmark.py`,
`wfzyx/von@master`, fetched 2026-09-24): the labels buffer, the depth buffer,
and 3 game variables, serialized to a sentence, scored as a 3-option
`choice`. The vision arm (raw frames, PRD.md 8.1d step 8) is deliberately
scoped out of this build -- see "What this harness does not do yet" below.

## What was verified, for real, on this server (CPU only)

- **The bucket boundaries are byte-faithful to Von's `format_doom_state()`**
  -- `python -m benchmarks.vizdoom.observe` unit-tests all five position
  buckets, four size buckets, and four depth buckets against hand-built
  snapshots, plus two full-sentence renders. Passes.
- **`DoomEnvironment` reproduces Von's exact config against the real,
  running ViZDoom engine**, headless (`DISPLAY=` empty, no xvfb): stock
  `.cfg`/`.wad` from `vizdoom.scenarios_path`, `RES_320X240`, RGB24, HUD off,
  crosshair on, labels + depth buffers on, sound off, the right 3-button
  action set per scenario, `tics=4`, 300-step cap. **The
  `get_available_buttons()` order assertion actually ran and passed** for
  both scenarios -- not just written, exercised, on real engine state.
- **A real kill was actually registered** in a throwaway smoke episode
  (`seed=42106076`, 20 `attack` steps -> `kills=1`) before any harness code
  ran against it, confirming the game-variable read and the action-to-button
  mapping are both wired correctly, not just type-checking.
- **The full episodic loop runs end to end against the real engine**: both
  scenarios, both rubric conditions, `--backend decoder-multischema-mock`
  (non-trained keyword-overlap heuristic, no torch/transformers/peft/
  checkpoint) -- 4 evidence bundles committed under `results/vizdoom-
  {defend_the_center,health_gathering}-{von,none}-decoder_multischema_mock-*`.
  This is a wiring proof only; the mock's `rubric_agreement` numbers mean
  nothing about game understanding (same discipline as every other Mock
  backend in this repo).

## Baseline policies, run for real (PRD.md 8.1d checklist steps 3 and the random-baseline reproduction)

**1. The rubric-oracle baseline** (`--policy oracle`) -- Von's own 4-clause
rule, run directly as a policy with no model, no GPU, a few CPU-seconds
(`benchmarks/vizdoom/rubric.py::rubric_action`). 8 published seeds, 1 episode
each, `--rubric von`:

| Scenario | Oracle (this harness) | Von (published) | Jev (published) |
|---|---|---|---|
| `defend_the_center` kills | **11.125** (sd 2.03) | 9.00 | 5.62 |
| `health_gathering` survival s | **19.71** (sd 7.02) | 12.11 | 13.03 |

`rubric_agreement` is exactly **1.0** for both, by construction (the oracle
*is* the rubric) -- a real sanity check that the scoring path works, not a
result in itself.

**Honest caveat, stated rather than spun**: the oracle scoring *above* Von's
own published number is a genuinely interesting finding, but it rests on one
modeling choice this harness had to make that Von's own `instructions` text
doesn't disambiguate -- which enemy/medkit governs the decision when more
than one is visible. This harness's oracle always attends to the *nearest*
(largest-apparent-size) one (`env.py`'s `DoomSnapshot.things` is sorted
largest-first). That is a reasonable reading, not a verified-against-Von's-
model reading. What it *does* license saying: **a purely mechanical, zero-
learning execution of Von's own published rule is enough to match or exceed
Von's own reported score**, evidence toward (not proof of) PRD.md 3.1's claim
that Von leans heavily on rubric text rather than learned game
understanding. The real `--rubric von` vs `--rubric none` gap (once a real
checkpoint runs) is the more decisive test of that same claim -- see Finding
3 in PRD.md 8.1d.

**2. The random-policy baseline** (`--backend random`), reproducing the
planning pass's own probe methodology exactly (8 seeds x 10 episodes each,
uniform random over the 3 available buttons, `tics=4`, seeds `0..7` rather
than Von's published big integers -- a random policy's behavior doesn't
depend on which 8 seeds are used, only Von's real-comparison protocol in
step 6 below does):

| Scenario | This harness (n=80 episodes) | Planning-pass probe | Von's own published random |
|---|---|---|---|
| `defend_the_center` kills | **1.275** (sd-across-seeds 0.19, per-seed range 0.9-1.6) | 1.53 (sd 0.39, range 0.9-2.0) | 1.88 |
| `health_gathering` survival s | **14.65** (sd-across-seeds 1.22, per-seed range 13.17-16.91) | 14.09 (sd 1.03) | 15.77 |

**Both numbers land in the same ballpark as the probe's own independently-run
measurement** -- this is the sanity check PRD.md 8.1d's implementation
checklist asked for, confirming this harness's environment loop and metric
extraction match the verified probe's methodology, not a second, disagreeing
implementation. The qualitative finding stands unchanged: `health_gathering`
survival (14.65s here) already exceeds Von's published 12.11s from a policy
with zero intelligence, so it does not discriminate as configured (PRD.md
8.1d Finding 2) -- reported here again, with this harness's own real number,
not just cited from the probe.

Evidence bundles: `results/vizdoom-defend_the_center-von-random-*`,
`results/vizdoom-health_gathering-von-random-*`,
`results/vizdoom-*-rubric_oracle-*`.

## DAgger-teacher data emission (PRD.md 8.1d Finding 4 point 3 / 5.3b)

Wired and validated, not yet consumed by anything. `--dagger-out <dir>` makes
every tick of a text-arm rollout emit a `(text, frame, teacher_action)`
triple -- `benchmarks/common/episodic.py::DaggerSink`, whose docstring is the
authoritative source for the storage format (`triples.jsonl` + `frames/
*.png` per run, gitignored under `training/dagger_data/`). Run for real
during this build: `--backend decoder-multischema-mock --dagger-out
training/dagger_data/vizdoom` on `defend_the_center`/`von`/seed
`42106076` produced 90 real JSONL rows and 90 matching real PNG frames
(320x240x3, pulled from the real `screen_buffer`), e.g.:

```json
{"episode_index": 0, "frame_path": "frames/defend_the_center_von_42106076_0_0000.png",
 "model_action": "attack", "rubric": "von", "scenario": "defend_the_center", "seed": 42106076,
 "state": "Arena Combat Situation: ... A chainsaw marine is visible dead center on the crosshair, far away. ...",
 "teacher_action": "attack", "tick": 0}
```

This data is gitignored (real, regenerable, per-checkpoint rollout output --
same discipline as `checkpoints/` and `results/*.raw`) and nothing downstream
reads it yet; it exists so the day a vision-arm trainer is built, the
data-collection half is already done and already validated end to end.

## Rubric conditions (PRD.md 8.1d Finding 3)

Both are always run, never just one:

- **`--rubric von`**: Von's own `instructions`/`criteria` strings verbatim
  (vendored Apache-2.0 data, see `NOTICE.md`) -- the headline like-for-like
  number, comparable to 9.00/5.62.
- **`--rubric none`**: a bare task description naming the goal and the
  action set, no if/then rule.

The **protocol conversion** (Von's `Choice.criteria` option->criterion
mapping -> this project's flat `options` + `instructions` string) is
deterministic and documented in `rubric.py`'s module docstring; verified at
import time that `criteria.keys()` order already matches each scenario's own
action order, so no reordering is needed.

## What this harness does *not* do yet

- **Not run against a real trained checkpoint.** `checkpoints/
  ekvachan-decoder-qwen-benchcorpus` already exists and is validated
  (13a.7/13a.10) -- the real run needs no GPU wait at all, but this session
  was explicitly scoped to never touch the GPU while the vision training run
  was active. See "Running" below for the exact command.
- **No vision arm.** `observe.py::observe_frame()` is a documented
  `NotImplementedError` stub (PRD.md 8.1d step 8) -- built after
  `checkpoints/ekvachan-decoder-qwen-vision` lands and ScreenSpot-v2
  produces its first real number. The DAgger emission above already writes
  the frames that arm will eventually train on.
- **No StarCraft or browser-use harness** -- explicitly out of scope for
  this build (PRD.md 8.1d), separate design questions, neither blocks this
  comparison.

## Running

```sh
# THE milestone: real text-arm run against Von's own published protocol,
# both scenarios, both rubric conditions, all 16 published seeds --
# needs nothing that doesn't already exist:
python -m benchmarks.vizdoom.run --backend decoder-multischema \
    --checkpoint-dir checkpoints/ekvachan-decoder-qwen-benchcorpus \
    --scenario both --rubric both

# Rubric-oracle baseline -- no model, no GPU, no checkpoint:
python -m benchmarks.vizdoom.run --policy oracle --scenario both --rubric von

# Random-policy baseline, this session's own validation methodology
# (8 seeds x 10 episodes, matching the planning-pass probe):
python -m benchmarks.vizdoom.run --backend random --scenario both --rubric von \
    --seeds 0,1,2,3,4,5,6,7 --episodes-per-seed 10

# Harness wiring self-test -- real ViZDoom episodes, no torch/transformers/
# peft/checkpoint:
python -m benchmarks.vizdoom.run --backend decoder-multischema-mock --scenario both

# With DAgger-teacher data emission:
python -m benchmarks.vizdoom.run --backend decoder-multischema-mock \
    --dagger-out training/dagger_data/vizdoom
```

Every run writes evidence bundles to `results/` (`<run_id>.manifest.json` +
`<run_id>.raw`, one per scenario/rubric combination), same as every other
benchmark in this repo (PRD.md 8.2, `benchmarks/common/evidence.py`).
